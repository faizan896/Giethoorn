# Decision: controlled recorded-data IOC scenarios, paper version 3

Status: implemented for offline protocol and cost testing. There is no adaptive
strategy, live feed/order adapter, wallet or funded execution. The 24-hour
reliability gate remains pending. These scenarios do not establish profitability.

## Compatibility and provenance

Paper versions 1 and 2 keep their exact golden output and restrictions. Version 2
still rejects orders/fills. Version 3 uses `recorded_execution` provenance, binding
the source recording fingerprint, operator-declared origin, raw scenario SHA-256,
selected feed/network and exact execution assumptions to every update. The
accounting model remains `linear_contract_fifo_v1`; the fill-model identifier is
`assumed_next_fresh_quote_ioc_v1`.

The scenario has version 1, a printable label, fixed risk/account limits, explicit
fee/slippage/liquidity/timing assumptions and 1–64 unique orders sorted by original
market sequence. Each order specifies side, quantity, limit and the source event
after which to request it. Requests are predeclared, not generated by a strategy
or chosen from future prices. A source end/unknown event cannot be an anchor.

The existing finalized schema-2 reader validates and privately copies the source.
The scenario is persisted unchanged before processing. Every derived paper input
is synchronized before ledger application. Source links remain contiguous in
paper sequence but can repeat a market sequence for simulated actions. A separate
trace distinguishes market events, scenario requests, assumed acknowledgements,
fills, cancellations, expiries and the generated replay end. Original data and
historical supervision counters are never rewritten.

## Timing and eligibility

Source records process first, then previously pending simulated arrivals, then
new scenario requests. The risk ledger checks each request against the current
recorded mark and exposure. Missing/stale/disconnected data, loss halts and limit
breaches can reject a request before it enters the pending-arrival list.

The assumed arrival is request monotonic time plus `latency_ms`. Execution uses
the first **new selected-feed usable quote** after the request with time at or
after arrival and strictly before arrival plus `quote_wait_ms`. Depth cannot fill
a BBO-selected order, and an existing mark or triggering quote is not an execution
opportunity. An observed event at/after expiry produces an explicitly simulated
expiry rejection, even when that event carries a fresh quote. There is no clock
interpolation, wall-clock scheduling, randomness or look-ahead.

Acknowledgements and IOC remainder cancellations are assumed immediate at the
chosen opportunity. This is an offline model, not a venue timing measurement or
order-reconciliation policy. If the source ends before opportunity/expiry is
observed, the order remains pending. Replay completion never invents its ACK,
flattens inventory or releases unresolved exposure. Already in-flight fills remain
accountable after a loss halt; the halt blocks new requests.

## Price, liquidity and cost assumptions

Only marketable IOC limit orders are modeled. Buy touch is the recorded best ask;
sell touch is the best bid. The assumed price is touch multiplied by
`1 + slippage_bps / 10000` for buys and `1 - slippage_bps / 10000` for sells. A price
beyond the order's limit produces no fill. There are no guaranteed maker-touch
fills, resting-order queues or depth walking.

Fill quantity is capped by the remaining order quantity and an explicitly assumed
fraction of that opposite top level's **recorded size**. Concurrent orders share
the capacity. Equal exchange timestamps do not replenish consumed liquidity;
equal-time price changes conservatively disable further capacity until a new
timestamp/connection. A filled order has one assumed IOC fill. Any unfilled
remainder receives simulated cancel-request and cancel-ACK events.

Fees are `assumed fill price × quantity × declared fee rate`, charged once by the
existing exact ledger. Spread cost is `abs(touch − recorded mid) × quantity`;
slippage cost is `abs(fill price − touch) × quantity`. The latter two are a
decomposition already reflected in execution prices, not extra account debits.
Every event carries cumulative cost receipts calculated with exact Rust amounts.
No rounding, floats or browser financial calculations enter the ledger.

The model is uncalibrated. It does not model venue increments/minimums, matching
queues, market impact, funding, margin/liquidation, fee tiers/rebates or private
order-channel failures. Displayed public size does not guarantee actual execution.

## Bounds, export and acceptance

Scenario input is capped at 64 KiB; fixed orders at 64. Source bounds remain those
of the finalized-recording adapter. A conservative event-count reservation keeps
all source and generated actions within 10,000 paper events. Output limits and
create-new/private-file behavior remain enforced. Errors retain diagnostics and
never publish a success view. There is no source truncation or automatic repair.

`ops/paper_execution.py` checks source/scenario fingerprints and event references,
independently replays the saved paper ledger, and verifies price, size, timing,
fee/spread/slippage and balance algebra using Python Decimal with 100-digit
precision. The browser renders the resulting states and cumulative costs; it
does not execute orders. Real captures and synthetic fixtures keep distinct
origin labels and all execution remains explicitly simulated.

The reviewed synthetic scenario produces two partial fills, IOC cancellations,
missing/stale/risk rejections, an expiry-boundary rejection and one unresolved
pending order. Its round trip ends flat with realized P&L `-0.0300225`, fees
`0.02511250125` and net P&L `-0.05513500125`. Spread cost `0.05` and adverse
slippage `0.0050225` are already embedded in fill prices. These are hand-calculated
test vectors, not measured strategy returns.

Tests cover exact repeat/golden output, latency and causal source selection,
expiry boundaries, partial/cancel states, shared capacity, equal-time updates,
limit-price protection, future-price independence, risk/loss halts, unresolved
end states, provenance/version separation and corrupt/active source rejection.

Next is empirical calibration and a broader scenario/data-quality suite before
strategy evaluation. Live integration still requires its own reliability,
execution and reconciliation acceptance; this offline capability enables none
of those implicitly.
